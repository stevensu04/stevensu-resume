## 1. Positioning

Everything on this site is a variation of one sentence:

> **Full-stack developer who came from banking — I ask why the workflow exists before I write the code that replaces it.**

**Why this sentence.** The career change is the differentiator, not something to apologise for. Most
grad-market competitors are "passionate about full-stack." Almost none of them have sat client-side in
a bank for two years and can read a business problem before writing code. Lead with the thing nobody
else can say.

**Words that are banned from the site:** "student" (reads as *not ready*), "passionate about" (reads as
*no evidence*), "freelancer" (competes with "hire me full-time").

**The designer claim is dropped.** Not the design *work* — ParkEase and the HCI research stay, because
"engineer who does user research before building" is a strong supporting story for a grad SWE. But the
site no longer asks to be believed as a designer. Claiming two identities at entry level gets you
credited for neither.

Single source of truth for all messaging: `src/lib/site.ts`. Change the pitch there, it changes everywhere.

### Not on the site
Possible move back to Taiwan in ~2 years. A grad program is a multi-year investment; signalling a
planned exit is a reason to pick someone else. Omitting a hypothetical is not dishonesty. It does have
one quiet implication worth acting on: prefer employers with APAC presence or remote flexibility, so a
future move is a transfer rather than a resignation.

## 2. The core problem

The portfolio's weakness is not visual. It's **verifiability**.

A full-stack reviewer checks three things: *is it deployed, can I see the code, does it run.*

| Project | What it actually is | Engineering evidence |
| --- | --- | --- |
| BrisPulse | Concept + simple responsive prototype | Systems thinking, not code |
| Finance Forms | Real, shipped, QLD Government — but low-code | Delivery, not code |
| ParkEase | Figma prototype + HCI research | Design research |
| JourneyMate | Vanilla JS/HTML/CSS, live on GitHub Pages | Modest, but real and running |

**There is no substantial running codebase in the portfolio.** Every other item in this plan is polish
on top of that gap. Phase 2 is the one that actually moves the needle; Phases 0/1 stop the site from
actively costing credibility while Phase 2 is in progress.

## 9. Phase 6 — 3D tech-stack orbit (replaces the badge cloud)

**Decided:** two rings grouped by layer · drag-to-spin included · mobile gets a static grid.

### Why the current cloud is asymmetric

Not because it's 2D. Three causes, in order of weight:

1. **Mixed label shapes.** Eleven short tech names against four long phrases —
   `Cross-cultural Communication` is 28 characters, `SQL` is 3. Any radial arrangement collapses when
   item widths vary by 4×: a wide pill is enormous at the front of an orbit and vanishes at the side.
2. **Counts of 11 vs 4.** Dense left, sparse right. Positioning cannot fix an unequal split.
3. **The circle does no work.** The `bg-blue-50` disc, the `</>` watermark and the badges are three
   unaligned visual systems; the badges sit *beside* the circle, not on it.

Note: the Phase-0 offset clamp (§4) fixed a real collision but flattened the left arc into a
near-vertical wall, which made cause #1 more obvious.

### Prerequisite: remove the four professional skills from the hero

`Stakeholder Engagement`, `Process Analysis`, `Business Documentation`,
`Cross-cultural Communication` leave the hero. Two reasons:

- **Layout:** the remaining 11 tech names are similar widths, so even distribution becomes automatic.
- **Positioning:** they are business-analyst vocabulary competing with the engineering signal in a
  hero aimed at grad SWE roles — the same hedging Phase 1 removed elsewhere.

They are real strengths and get relocated, not cut. **Blocked on reading Steven's latest resume**
before choosing placement (likely inside the About banking narrative).

### Structure

Two counter-rotating rings, tilted ~15° on X, sharing one perspective container:

| Ring | Radius | Contents | Direction |
| --- | --- | --- | --- |
| Upper — Frontend | ~230px | Next.js, React, TypeScript, Tailwind CSS, Figma | +ω |
| Lower — Backend & Data | ~260px | Python, Django, Java, SQL, GitHub, Power Platform | −0.75ω |

Ring membership replaces the six arbitrary badge colours as the meaning-carrying signal, and makes
the graphic argue the `From the bank floor to full-stack.` headline rather than decorate it.
Counter-rotation supplies parallax, the cheapest convincing depth cue available.

### Ring math

Everything derives from one scalar per ring, so a frame costs two CSS custom-property writes.

```
item i of n:   θᵢ = (360/n)·i
placement:     rotateY(θᵢ) translateZ(R)
billboard:     rotateY(−(θᵢ + rot))        ← cancels rotation; face always toward camera
depth:         d  = (cos(θᵢ + rot) + 1) / 2     0 = back, 1 = front
               opacity = 0.40 + 0.60·d
               scale   = 0.85 + 0.15·d
               blur    = (1 − d) · 2px
               zIndex  = round(d · 100)
```

**Billboarding is the technique that makes the whole idea viable** — it satisfies the
「用平面的視角看到所有 tech stack」 requirement. Position moves through 3D; each badge face stays flat
to the viewer, so nothing is ever mirrored or unreadable.

Driven by CSS custom properties (`--rot` on the rotor, `--angle` per badge) so one variable write
updates every badge, rather than re-rendering 11 React nodes per frame.

### Camera — the "director's angle"

| Cue | Setting | Purpose |
| --- | --- | --- |
| Tilt | `rotateX(15deg)` | Head-on reads flat; a slight downward look reads as 3D immediately |
| Perspective | `1200px` | Lower is dramatic, higher is subtle |
| Depth of field | blur/opacity/scale falloff per the math above | The single biggest cinematic cue |
| Fog | radial mask at ring edges | Items fade rather than clip |
| Easing | damped spring, never linear | Linear rotation reads as mechanical |

Depth-of-field is also what lets 11 badges coexist without noise: the back half recedes instead of
competing.

### Motion — three layers

Scroll-driven rotation *alone* fails here, and it's worth being explicit about why: the hero is the
first screen. A visitor who hasn't scrolled sees a frozen object, and by the time they scroll the
hero is already leaving the viewport — roughly 600px of travel, spent while the element exits.

1. **Base** — continuous auto-rotation, ~40s per revolution. Alive from first paint, which is when
   the impression forms.
2. **Scroll** — adds angular *velocity*, not absolute position. Spins faster while scrolling, decays
   back to base. Feels physical.
3. **Drag** — pointer drag with inertia and momentum decay.

```
ω = ω₀ + ωimpulse ;  ωimpulse *= 0.94 per frame ;  rot += ω·dt
```

**No scroll-jacking.** The page scrolls normally and the object merely responds. Pinning the viewport
while an animation plays is not compatible with claiming HCI credibility.

### Technology: CSS 3D + Framer Motion. Explicitly not Three.js.

|  | CSS 3D + Framer Motion | Three.js / R3F |
| --- | --- | --- |
| Bundle | **0 KB** — Framer Motion already a dependency | +600 KB |
| Text | Real DOM — accessible, selectable, crawlable | WebGL text needs troika or a DOM overlay |
| Perf | GPU-composited; trivial for 11 elements | Overkill at this scale |
| LCP | No impact | Risks the above-the-fold paint |

`transform-style: preserve-3d` + `rotateY` + `translateZ` delivers everything specified above. For
eleven pills, WebGL buys nothing and costs the hero's load time and its accessibility.

### Non-negotiables

- **`prefers-reduced-motion`** → static grid, no rotation, no RAF loop. Via framer-motion's
  `useReducedMotion()`. Not optional on a site claiming HCI.
- **Below `lg` → static grid.** Rings go tiny on phones and it is the worst place to spend the
  performance budget. The 3D is a desktop reward.
- **Semantics** — a real `<ul>`/`<li>` of skills underneath the transforms; screen readers get a list
  regardless of what the transforms do.
- **Perf budget** — transform/opacity/filter only, one RAF loop for both rings, `will-change` on the
  two rotors only, blur capped at 2px. The `<h1>` must remain the LCP element.

### Files

- `src/lib/stack.ts` — tech stack grouped by layer (single source, like `site.ts`)
- `src/components/TechOrbit.tsx` — 3D component, with the static grid as its own fallback branch
- `src/app/page.tsx` — swap out the badge cloud

### Verification checklist

- [x] **Billboarding** — pill width measured at `--rot` 0/90/180/270: 96 → 81 → 67 → 81px. Never
      collapses (a broken billboard would go edge-on to ~0); the shrinkage is depth scale ×
      perspective, as intended.
- [x] **Orbit geometry** — badge centre swings 988 → 1153 → 988 → 823px, i.e. ±165px about the
      centre, matching the 168px radius.
- [x] **Depth of field** — opacity 1 → 0.67 → 0.34 → 0.67 and blur 0 → 1 → 2 → 1px across the same
      sweep. Matches the specified curve exactly.
- [x] **Counter-rotation** — rings carry opposite-signed `--rot` (+1 / −0.75).
- [x] **`cos()` support** confirmed; `@supports` fallback in place regardless.
- [x] 1440 and 375 — no horizontal overflow, no collision with hero text.
- [x] Mobile → orbit `display:none`, grid `display:flex`, 11 pills inside 375px, no overflow.
- [x] `prefers-reduced-motion: reduce` rules parsed and live in the stylesheet.
- [x] Accessibility — grid is the semantic source (`sr-only` on desktop, visible on mobile); orbit
      is `aria-hidden`. AT gets a labelled list of 11 skills at every breakpoint.
- [ ] 60fps under sustained scroll + drag — **not yet observed.** The automated browser pane runs
      backgrounded (`visibilityState: "hidden"`), so `requestAnimationFrame` is throttled to zero by
      the browser and the live motion could not be watched. The rotation loop demonstrably starts
      (`--rot` advanced before the pane hid) and the transform math is verified above, but the
      *feel* — base speed, scroll gain, drag inertia — needs a human look in a real window.
- [ ] Drag does not hijack vertical page scroll on touch — `touch-action: pan-y` is set; untested on
      a real touch device.

### Cost and sequencing

~1 focused day, plus ~half a day for drag. No new dependency; the math is roughly 20 lines.

**This does not outrank Phase 2.** BrisPulse having no running code is still what decides interviews;
a hero animation is not. Build this as a break from that work, not instead of it. The honest
counter-argument: for a frontend-leaning full-stack role a well-built scroll-reactive 3D component
*is* portfolio evidence — coordinate math, RAF scheduling, reduced-motion handling, responsive
fallback are all engineering a reviewer can see working. That holds only if it's built to the
standard above.
